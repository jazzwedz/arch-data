# 1. Business needs / Business requirements

## 1.1 Business value

**What is the added business value?**

For effective portfolio and risk management, it is essential to accurately classify corporate clients
based on their actual economic activities. However, a standardized and systematic way of capturing
these activities is currently lacking. Instead of a clear industry classification, only internal risk
labels are available. These are driven by product and underwriting considerations and do not provide
a clear or consistent description of the underlying economic activity. As a result, risks, industry
exposures, and activity clusters can only be analyzed to a limited extent.

In the insurance business, risks vary significantly depending on the economic activity involved.
Sectors such as construction, manufacturing, hospitality, healthcare, or financial services exhibit
fundamentally different loss profiles, risk drivers, and regulatory frameworks. Without a uniform and
structured classification of these activities, such differences cannot be adequately reflected in
underwriting processes or in strategic portfolio steering.

The `NACL` code provides an officially recognized, nationally standardized classification of economic
activities maintained by the public statistics authority. Introducing it at the corporate level
enables a clear and consistent representation of a client's activity. This creates the foundation for
more precise risk models, improved claims and industry analyses, and transparent reporting across the
entire portfolio.

Capturing the `NACL` code — particularly via systems such as the `[EXTERNAL REGISTRY CODING TOOL]`
and independently of the distribution channel — enables, for the first time, a consistent,
cross-sales view of industries and activities. This not only significantly improves data quality, but
also establishes the basis for efficient reporting, targeted portfolio analyses, regulatory
compliance, and effective strategic steering.

**What is the consequence if this change is not implemented? E.g. regulatory topics, competitiveness …**

If the `NACL` code is not introduced, the company will continue to lack a uniform and standardized
industry classification. As a result, the economic activities of our corporate clients can only be
inferred from internal risk labels, which are not sufficiently differentiated and are not suitable
for portfolio or risk analyses. This means that key management functions such as underwriting,
product management, portfolio analysis, and risk management lack a reliable basis for assessing
industry exposures, loss profiles, and market segments.

Without `NACL`, there is no clear overview of industries and no consistent view across the entire
commercial portfolio.

This not only complicates strategic market development and customer segmentation, but also leads to
limited transparency regarding risks and activity clusters. In addition, significant efficiency
potential remains untapped, as manual adjustments and data cleansing continue to be necessary.

In short: without the introduction of the `NACL` code, data quality remains low, portfolio analysis
incomplete, and strategic corporate steering constrained.

## 1.2 Description

**What is this change about?**
*Please indicate what you would like to have, what is the expected outcome, which teams, processes and/or products/guarantees are concerned.*

**Current situation:**

At present, no standardized industry classification such as the `NACL` code is stored at the company
level in `CORE`. As a result, a clear and structured assignment of our clients' economic activities is
not possible.

For reporting and portfolio analyses, only the risk labels recorded in the system are used. However,
these are based on product-specific or underwriting-driven risk assessments and do not correspond to
an official, industry-based classification of the company's actual economic activity.

This means that, across the entire commercial business, there is no uniform and consistent industry
classification that can be reliably applied across all distribution channels. This makes
comprehensive portfolio analysis more difficult, as well as targeted customer segmentation and the
transparent representation of activity and industry clusters. Consequently, a consistent assessment
of our clients' economic activities is currently not ensured.

**Target situation:**

We aim to introduce a uniform and officially recognized industry classification for all Commercial
products (`[FOUR COMMERCIAL PRODUCT LINES — names removed: a commercial all-lines product, a modular
commercial product, a motor fleet product and a diversified commercial product]`) across both `V2`
and `V3`. To achieve this, the `NACL` code — or a complete `NACL` classification list — will be newly
integrated into `CORE` at the partner/company level.

### 1.2.1 Target state: desired mapping of the `NACL` code in `CORE`

We would like to integrate a search and selection functionality for the `NACL` code analogous to the
existing implementation for "Type of Employment / Occupation". Users should be able to select the
`NACL` code following the same principle, i.e. via a search field with a list of results and a
structured display of relevant information.

In addition, the `NACL` search will be enhanced with a hierarchical tree view of the classification
system. In line with the logic used in the `[EXTERNAL REGISTRY CODING TOOL]`, a search by keyword or
by partial or full code should not only return the 6-digit activity code but also display its
position within the full hierarchy.

The hierarchical structure includes:

- Section
- Division
- Group
- Class
- Category → 6-digit activity code

The tree structure serves purely for orientation and for the professional classification of the
economic activity. Only the 6-digit activity will be available for selection and storage in the
system.

**`NACL` Code / `NACL` Description (Primary Activity of the Company)**

The search and selection interface should provide the following information:

- A search bar with a magnifying glass icon at the top (keyword search).
- **Keyword search**
  - Search by text (e.g. an industry word such as "restaurant", "IT", "carpentry")
  - Search by codes (e.g. a 4-digit class such as `[NN.NN]`)
  - The system displays matching suggestions.
- **Autocomplete / suggestion list** — as users type keywords or codes, `CORE` automatically returns
  relevant codes, including their descriptions.
- Within the search and selection field, the full code together with its description is displayed
  (e.g. `[NN.NNN]` – *computer consultancy activities*).
  → **Important:** users can search both by code (full or partial) and by keywords.
- Below this, a results table is displayed with multiple columns:
  - `NACL` Code (6 digits)
  - `NACL` Description
- Since `NACL` does not include risk classes, colour logic, or product-specific attributes, the
  following columns are **not** applicable: risk number, product, traffic light (colour coding).
- As with "Type of Employment / Occupation", the user should be able to select an entry with a single
  click.
- The selected 6-digit code will then automatically:
  - be entered into the partner master data record
  - be validated as a mandatory field
  - be stored in the system

**Data source: the official classification list**

The complete classification list is provided by the national statistics authority and is available in
`[LANGUAGE VERSIONS REMOVED — the language set identifies the market]`. The dataset will be attached
to the corresponding ticket and serves as the authoritative data source for the implementation.

**Mandatory field logic**

The `NACL` code is:

- Mandatory when creating a new company
- Mandatory for master data changes if activities have changed
- Mandatory for contract changes → error message if no code is selected

The code must already be defined as a mandatory field when creating a new partner or company.

- **New business:** the code must be captured for every new business case.
- **Existing portfolio:** a list has been created for existing corporate clients, where each client
  has already been assigned a unique code. For these clients, an initial pre-population of the code
  should be loaded into `CORE` from the existing portfolio list (only those marked as confirmed),
  provided the information is already available. This ensures an initial, systematic classification
  of the economic activity for the existing customer base.

In addition, during the next update of the company (e.g. master data change, contract change,
renewal), the system should automatically check whether a code is present and whether it is still
plausible.

- If no code is stored, it must be entered (mandatory field).
- If an update may be required, the system should display a prompt indicating that the code needs to
  be reviewed and adjusted if necessary.

The objective is to gradually complete and validate the codes in the existing portfolio without
blocking ongoing processes, while sustainably improving data quality through future updates.

**Location of the future `NACL` field**

`[FIGURE REMOVED — screenshot of the current company master data screen]`

Since the `NACL` code describes the company's primary economic activity and is not captured at the
product level, it should be recorded directly at the company level.

Positioning in `CORE`: the field should ideally be integrated within the "Modify Company" section,
under "Identity", as it represents a fundamental master data attribute.

The existing field "Type of Company" should be replaced with a selectable `NACL` code (6-digit, based
on the complete classification list).

In addition, a link to the `[EXTERNAL REGISTRY CODING TOOL]` should be integrated into `CORE` to
support the identification of the correct code. The implementation should follow the same approach as
the existing `[COMPANY REGISTER LOOKUP LINK]` and serve as guidance for users when selecting the
code. `[EXTERNAL URL REMOVED]`

If this section is not technically suitable, we require an alternative proposal for a functionally
appropriate placement within the company master data.

### 1.2.2 Reporting requirement

**Objective of introducing `NACL` coding**

The objective is to enable structured and consistent portfolio reporting from the system (`CORE` `V2`
and `V3`). This includes, in particular, analyses such as:

- Number of partners/customers per code
- Number of policies per code
- Additional aggregated key figures at both partner and policy level

The coding thus serves as a central classification dimension for industry analysis, which can be used
for both portfolio reporting and management reporting.

The 6-digit code is captured at partner level and represents the partner's primary economic activity.
This code constitutes the main and unique industry classification of a partner:

- Exactly one unique code is permitted per partner
- Multiple assignments or secondary activities are explicitly excluded
- The quality of reporting is based on a clear definition of the primary activity

The code is stored as a separate attribute in the partner table and can be directly used for
analysis.

**Historization and principle of data currency:**

- The partner table always contains the current and factually correct code of the partner
- Changes in the partner's main economic activity or updates to the classification system (e.g.
  revisions) should lead to an update of the code
- The system does not maintain parallel or outdated codes at partner level

The partner table is linked to downstream tables (e.g. policy table). This enables consistent
analyses at partner level, at policy level and at deeper functional levels (e.g. number of policies,
premium volume, or claims figures per code).

The business decoding of the code (e.g. its description) as well as the mapping of hierarchical
levels is not handled directly within the partner table but via a separate mapping table.

This mapping table includes, among others:

- Category: 6-digit code (key)
- Description
- Additional levels: Section, Division, Group, Class

This mapping table contains the hierarchical tree structure described above and can be used for
visualization purposes.

As a result, hierarchical aggregation and flexible analysis at different levels of granularity (e.g.
section or division) become possible without creating redundancies in the partner data model.
