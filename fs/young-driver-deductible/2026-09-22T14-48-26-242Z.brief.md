# Coding brief — Young Driver Deductible

> Generated by Team Repository on 2026-09-27 from the Functional Specification "Young Driver Deductible v2". One file, self-contained: everything an implementation agent needs is here. The FS is the source of truth for behaviour — where this brief and the FS disagree, the FS wins.

## 1. Mission

Build the Young Driver Deductible capability so that policyholders/owners and recorded drivers under an age threshold trigger a separate, age-based deductible for liability and collision on passenger cars, motorcycles and delivery trucks, consistently applied across quoting, policy issuance, documents, claims and CRM follow-up. This requires extending Customer Portal (DOB capture, young-driver question, raised deductible cap) and User Database (DOB storage), and building new components — Policy Core System (CORE), Young Driver Deductible Engine, Correspondence & Documents Service, Claims Deductible Validator, CRM Sales Opportunity Connector, SEC-ADMIN Screen and OPS-VIEW Screen — while reusing API Gateway, Identity & Access Management, Document Archive, Enterprise Event Bus and Notification Service. The result must ensure the young-driver deductible is determined and stored without ever appearing on offer/policy/GPC documents, is automatically applied at claims for eligible policies, and generates a cross-sell notification to agents, all without introducing new access rights.

## 5. Work items — use cases

### UC-01 — Young driver deductible determination and application

**Actors / components:** Policyholder/Owner, Customer Portal, API Gateway, Policy Core System (CORE), Young Driver Deductible Engine, User Database, Correspondence & Documents Service, Document Archive, Enterprise Event Bus, CRM Sales Opportunity Connector, Notification Service, Claims Handler, Claims Deductible Validator

**Flow to implement:**
1. Policyholder/Owner → Customer Portal (sync): Enters DOB and answers young-driver circle question during quote
2. Customer Portal → API Gateway (sync): Submits quote/policy request
3. API Gateway — Routes request to policy administration
4. Enterprise Event Bus — Delivers event for cross-sell processing
5. Claims Handler — Creates claim recording driver and DOB

**Rules to implement:** RG-01 (Auto-route by policy version), RG-02 (No anonymous policy access), RG-03 (Per-tier rate limit), RG-04 (PII data residency), RG-05 (Request priority score), RG-06 (Throttle policy-holders under fraud review)

**Implementation notes:** Extend Customer Portal to capture policyholder/driver DOB and the young-driver circle question, and to enforce the deductible dropdown rules (selectable only at or above the regular deductible when 'Yes', fixed/greyed when 'No', extended cap vs unchanged standard cap). Build Policy Core System (CORE) to orchestrate the declaration at quote/offer/provisional-policy/policy issuance, call the new Young Driver Deductible Engine (which reads DOBs from the extended User Database) to compute the liability and collision deductible, and serve SEC-ADMIN and OPS-VIEW screens for underwriter visibility. CORE must trigger Correspondence & Documents Service to generate offer/provisional-policy/policy/GPC documents that show only the Yes/No declaration and deductible amount — never the DOB — archived via Document Archive, and must publish a young-driver-declared event on Enterprise Event Bus consumed by CRM Sales Opportunity Connector, which may call Notification Service to alert an agent. Build Claims Deductible Validator to read the policy from CORE at claim creation and auto-resolve standard vs young-driver deductible, applied once per guarantee, but only for policies of the new tariff generation or newer (older policies are out of scope). Edge cases to handle: under-threshold policyholder leaves deductible and screens unchanged with nothing stored; missing DOB or missing driver data must be handled before determination; multiple loss events/lines under one guarantee must not cumulate the deductible; all API Gateway rules RG-01–RG-06 (auth, routing by policy version, PII residency, rate limiting, priority scoring, fraud-review throttling) must be enforced on the underlying /api/policies/* and /api/claims/* calls.

## 7. Non-functional constraints

### Performance

- **NFR-02** — API Gateway must serve requests to `/api/policies/*` and `/api/claims/*` (including the young-driver quote/policy and claims-resolution calls of UC-01) within a maximum latency of 200ms. Percentile of measurement (p50/p95/p99) is not specified in the facts — target left unset for that detail.
- **NFR-03** — API Gateway must sustain a throughput of 12 requests per second. The actual allowed rate per tenant is computed by the per-tier formula in RG-03 (`allowed_rps = base_rps * tier_multiplier`); the values of `base_rps` and `tier_multiplier` per tier are not specified in the facts.

### Availability

- **NFR-04** — API Gateway must be available 99.99% of the time. Measurement window (monthly/annual) is not specified.
- **NFR-05** — API Gateway Recovery Time Objective (RTO) is 4. Unit of measure (hours/minutes) is not specified in the facts — target left unset for that detail.
- **NFR-06** — API Gateway Recovery Point Objective (RPO) is 10 minutes.
- **NFR-07** — API Gateway scales vertically only; no horizontal auto-scaling capability is defined. Scaling thresholds are not specified.

### Security & Data Protection

- **NFR-01** — The highest data classification recorded across all members of this solution is "public". This is the value carried in the component inventory; it is flagged as inconsistent with the fact that the solution stores policyholder and young-driver dates of birth (see open point in chapter 11).
- **NFR-08** — Every request to an `/api/policies/*` endpoint must carry an authenticated session (RG-02); an anonymous request is rejected. Exact rejection code/message is not specified in the facts.
- **NFR-09** — Any request carrying customer PII, including the policyholder's or the young driver's date of birth, must be processed only in EU regions (RG-04).
- **NFR-10** — The young driver's date of birth, once captured and stored in User Database, must never be displayed on the offer, provisional policy, policy or GPC documents generated by Correspondence & Documents Service. Only the Yes/No young-driver declaration and the resulting deductible amount may appear on these documents.

### Decisions

| Decision | Rationale | Decided by |
|---|---|---|
| The young driver's date of birth is stored in User Database but never displayed on the offer, policy, provisional policy or GPC documents. | Agreed during the exchange meeting with Legal and Legal Claims. | Legal / Legal Claims |
